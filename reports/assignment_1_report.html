Q1 · Mini Document Search Engine

Inverted indexing and preprocessing

The system represents each document as normalized terms and builds an inverted index: a mapping from each stemmed term to the document IDs where it occurs, along with its frequency in each document.

Preprocessing pipeline

StagePurposeExample
TokenizationExtract lowercase alphanumeric tokens while splitting punctuation and underscores.“Cats, running!” → cats, running
Stop-word removalRemove common function words that usually carry little retrieval value.the, and, were removed
StemmingConflate related inflected forms so they match a shared root.cats → cat, running → run

Index representation

inverted_index = { "comput": {"doc-01": 2, "doc-04": 1}, "retriev": {"doc-02": 3}, "index": {"doc-01": 1, "doc-03": 2} }

The count in each posting is the term frequency. During search, postings for distinct query terms are merged using OR semantics; documents are ranked by the sum of matched query-term frequencies. Ties are resolved deterministically by title and ID.

Automatic index maintenance

  • Manual entry and batch upload both validate document title/text, persist the updated collection, and index the new material under a re-entrant lock.
  • Writes use a temporary JSON file followed by replacement, reducing the risk of a partially written store.
  • New-document API responses include updated index statistics; the client refreshes active results and collection metrics immediately.

Q2 · Multiple indexing techniques

N-gram retrieval and comparison

Alongside the inverted index, the application stores an unstemmed word index and a character N-gram index. This makes partial-word search possible without scanning every document body.

How partial matching works

  1. Keep the raw lowercase words (without stemming) and record their document frequencies.
  2. Generate trigrams for a fragment, or unigrams/bigrams for very short fragments.
  3. Intersect the N-gram posting sets to identify candidate words.
  4. Verify that the full fragment occurs contiguously in each candidate word, eliminating false positives.
  5. Aggregate candidate-word frequency by document and rank the result list.

Search results and performance

Evaluation methodology

Every submitted query is executed against both indexes. The workbench displays the matching documents, each processed query-term frequency, total score, result counts, and median lookup time. This enables a direct and reproducible comparison.

Presentation in the application

  • Search view: toggles between Inverted Index and N-gram Index result lists without rerunning the query.
  • Index snapshot: shows the current exact/partial result count and median milliseconds.
  • Comparison ledger: retains the latest measurement per query and shows exact matches, partial matches, inverted time, N-gram time, and shared documents.
  • Document coverage table: identifies which documents each technique retrieved and their total frequencies.
  • Accessible summary: communicates both result counts and timings to assistive technology through a live region.
Interpretation: The timings are controlled microbenchmarks of preprocessing, lookup, result construction and ranking. They exclude network, rendering, initial warm-up, disk writes and index construction; hence small timing differences should not be over-interpreted.

Implementation quality

Validation, testing and deployment

Input validation and robustness

Upload safety

Only non-empty UTF-8 .txt files are accepted. A batch is fully validated before any document is added, preventing partial success for invalid input.

Request boundaries

Uploads are limited to 30 files and 5 MB; queries are limited to 500 characters. Malformed payloads return JSON errors.

Storage integrity

Document storage validates JSON at startup and uses atomic replacement on writes. Duplicate or invalid records are rejected.

Client safety

Source content is inserted through DOM text nodes rather than unsafe HTML, and cross-origin mutations are rejected.
